# Operanto Growth — Slice 6 discovery (documentation only)

Status: **discovery**. No migrations, runtime services, provider integrations
or navigation entries exist or may be created from this document. Runtime
implementation begins only after the WhatsApp staging pilot findings have
been reviewed and Slice 6 is explicitly commissioned.

Heritage note: Growth absorbs the internal BrandForge/MediaSync concepts.
Externally there is only Operanto; none of the internal names appear in
product surfaces.

---

## 1. Domain model (proposed)

The prototype branch (`origin/mediasync-communication-layer`, untouched)
proved the shape of three entities on obsolete tenancy (`Workspace`,
6-role matrix). Everything below is REWRITTEN onto `OrgContext` +
`requirePermission` + `scope(ctx)`; nothing is ported verbatim.

| Model | Purpose | Prototype precedent | Notes |
| --- | --- | --- | --- |
| `BrandProfile` | Voice, tone, language, dos/don'ts, example phrases; the guardrail input to every content generation | `BrandVoice` (`brand-voices.ts`, working) | Extend toward a full profile: audience, offer positioning, banned claims. Contains no customer personal data. |
| `ContentDraft` | A generated or hand-written piece of content, always local until explicitly published | `ContentDraft` + studio UI (working) | Reuses the AIAction/ApprovalRequest pattern from Slice 4: drafts are AI OUTPUT records, PII-reduced inputs, validated JSON, redaction joins retention. |
| `Campaign` | A named growth initiative with goal, period, target channel set and budget-of-effort | none (queue mock only) | Owns `CampaignItem`s; carries the attribution key (§4). |
| `CampaignItem` | One scheduled/published unit (post, article, template broadcast) with channel, scheduled time, publish state | `queue_social_post` tool + mock social adapter | Delivery-state machine mirrors Message: `DRAFT → APPROVED → QUEUED → PUBLISHING → PUBLISHED / FAILED`, monotonic, DRAFT/APPROVED permanently local — the Growth analogue of RECORDED. |
| `GrowthInsight` | A conversation-derived observation ("5 enquiries this week asked about X") that can seed a draft | `insight-create-post` (prototype) | Generated by an AI task over aggregate, PII-scrubbed conversation stats; never quotes customer content verbatim without staff editing. |
| `AttributionTouch` | Records that a conversation/customer arrived via a campaign (§4) | none | Append-only, ids-only. |

Explicitly NOT in scope for a first Growth slice: audience segmentation,
lead-reactivation broadcasts (needs the consent model extended to marketing
consent — see §7), multi-variant testing, paid-ads management.

## 2. Non-negotiable platform invariants (inherited, not new)

1. **No autonomous external publishing.** Approving a draft records it;
   publishing is a separate, explicit human operation with a server-side
   recheck chain — the exact WhatsApp `sendWhatsAppMessage` pattern. No AI
   approval, cron, workflow or background process may invoke a provider
   publish call. The one sanctioned FAILED exit is an explicit human retry.
2. **Provider code behind adapters, deny-by-default registry.** A
   `GrowthPublishAdapter` per destination; unknown channels have no adapter;
   an adapter that cannot resolve its destination refuses.
3. **Tenancy.** Provider credentials per organisation, AES-256-GCM under
   `OPERANTO_ENCRYPTION_KEY`, never in plaintext, never in audit metadata,
   decrypted only inside adapter calls. No cross-tenant fallback of any kind.
4. **Privacy.** Growth models join `eraseCustomer` and retention on day one
   (insights and drafts sourced from a conversation carry the conversation
   id; erasure redacts sourced content). Audit metadata is ids-only.
5. **Three-role model.** Reuse `templates:manage`-style granularity:
   proposed `growth:manage` (A/S) for profiles/campaigns, `growth:publish`
   (A/S) for the explicit publish operation, `growth:read` reuse via
   existing view permissions. No new roles.
6. **Feature flags.** Deployment-level `OPERANTO_GROWTH_ENABLED` plus
   per-connection publish gates, publishing default OFF — the WhatsApp
   stage-gate pattern.

## 3. Build vs integrate, per capability

| Capability | Recommendation | Reasoning |
| --- | --- | --- |
| Brand profile + drafting + studio | **Build** (port + rewrite) | Prototype proved it; it is core product surface; AI layer (provider-neutral, mock-default) already exists from Slice 4. |
| SEO/article generation + publishing | **Integrate (Outrank) via inbound webhook** | Outrank publishes to 10 CMS targets and exposes a generic webhook for custom pipelines ([integrations](https://www.outrank.so/docs/improvements), [docs](https://www.outrank.so/integrations)). Operanto's role is RECEIVING: an `/api/webhooks/outrank` route (signature-verified, store-then-process — the ChannelInboundEvent pattern) ingests published-article events as `CampaignItem`s for attribution, rather than Operanto driving Outrank. Zero publish-side risk; no Operanto-held Outrank credentials beyond a webhook secret. |
| Social scheduling/publishing | **Do NOT integrate Buffer; defer provider choice** | Buffer stopped accepting new developer app registrations on its REST API and its GraphQL API is a personal-key beta without third-party OAuth — explicitly not viable for a multi-tenant SaaS in 2026 ([status](https://postproxy.dev/blog/what-happened-to-buffer-api-alternatives-for-developers/), [Buffer docs](https://buffer.com/developers/api), [help center](https://support.buffer.com/article/859-does-buffer-have-an-api)). Options, in preference order: (a) **direct platform adapters** starting with Meta (Facebook Pages + Instagram) — we already run an Operanto-managed Meta app, webhook verification, encrypted per-org tokens and the Graph API client from Slice 5B, so the marginal cost of a `MetaSocialPublishAdapter` is low; (b) an aggregator with a real multi-tenant API (evaluate at implementation time; the field shifts quickly); (c) Buffer personal-key mode for a single-workspace pilot only, never as product architecture. Decision deferred to implementation with (a) as the working assumption. |
| Creative providers (images/video) | **Integrate behind a neutral interface** | Mirror the `AIProvider` pattern: `CreativeProvider` with `MockCreativeProvider` deterministic default; a live provider (e.g. OpenAI image API — deployment-level key, no per-org credentials) added behind a tenant flag + deployment opt-in, exactly like `OPERANTO_AI_LIVE_ENABLED`. Generated assets are org-scoped files with explicit retention; no customer PII ever enters a creative prompt (enforced by the same PII-reduction used in Slice 4 context building). |
| Multilingual content | **Build on existing AI layer** | `translateMessage` task exists as mock; production quality is a model/prompt question, not an integration. |
| Attribution | **Build** (§4) | Nothing off-the-shelf fits a conversations-first model. |

## 4. Campaign → conversation attribution

Attribution is deliberately modest and honest: exact keys only, no
probabilistic matching (the identity-ladder philosophy applied to growth).

- **Key**: every `CampaignItem` carries a short code (`cmp_<id>`), woven
  into published URLs as UTM parameters and, for WhatsApp entry points,
  into a `wa.me` click-to-chat link's prefilled text.
- **Capture rungs (exact only)**:
  1. Pronatona web enquiries: the existing signed event envelope gains an
     optional `campaignRef` field (additive, ignored when absent) carried
     from UTM → lead → `AttributionTouch`.
  2. WhatsApp: a first inbound message whose text still contains the
     prefilled campaign code attributes the conversation, then the code is
     stripped from display.
  3. Manual: staff can attach a campaign to a conversation (select field,
     audited) — the fallback that always works.
- **Storage**: `AttributionTouch { organisationId, campaignItemId,
  conversationId, customerId?, capturedVia }` — append-only, ids-only,
  joins erasure via `customerId`.
- **Reporting**: campaign detail shows touches → conversations → linked
  customers → tasks/opportunities created, all as counts with drill-down
  through existing scoped queries. No cross-org aggregation, ever.

## 5. Provider adapter interfaces (sketch)

```ts
// Publishing — mirrors ConversationChannelAdapter discipline.
interface GrowthPublishAdapter {
  readonly destination: GrowthDestination;      // e.g. META_PAGE, META_IG
  /** Validate connection ownership + credential; stamps health. */
  verifyConnection(connection: GrowthConnection): Promise<ConnectionStatus>;
  /** Explicit publish — called ONLY by publishCampaignItem's recheck chain. */
  publish(input: PublishInput): Promise<{ providerPostId: string }>;
  /** Normalize provider callbacks/metrics; data only, nothing executed. */
  receiveEvents(payload: unknown): NormalizedGrowthEvent[];
}

// Creative — mirrors AIProvider (mock default, live opt-in).
interface CreativeProvider {
  readonly name: string;
  generateImage(spec: CreativeSpec): Promise<CreativeAsset>; // no PII in spec
}
```

`publishCampaignItem(ctx, itemId, idempotencyKey)` re-runs server-side:
deployment flag → `growth:publish` → org + record access → item is
APPROVED (never DRAFT) → connection active + publish-gate + credential →
brand-profile safety checks → idempotency claim before the provider call →
conditional `QUEUED→PUBLISHING` claim → provider → `PUBLISHED`/`FAILED`.

## 6. Validation journeys

**Nagelista (retail):** an operator notices recurring gel-polish shipping
questions → `GrowthInsight` suggests an FAQ post → staff generates a draft
against the Nagelista `BrandProfile` (mock AI in staging) → edits, approves
(local) → explicitly publishes to the connected Facebook Page with a
campaign code → a shopper clicks the wa.me link and asks about the offer →
the inbound WhatsApp conversation carries the campaign code →
`AttributionTouch` links campaign → conversation → linked customer → order
follow-up task. Report shows the chain end to end.

**Pronatona (real estate):** a new listing seeds a campaign (article via
Outrank webhook ingestion + a social post) → a buyer submits the Pronatona
web form from the article (UTM → `campaignRef` in the signed envelope) →
lead event creates customer + opportunity with an `AttributionTouch` → the
buyer later writes on WhatsApp, identity ladder links them → campaign
detail shows: 1 article, 1 post, N enquiries, M viewings booked. Growth
never sends anything to the buyer autonomously at any point.

## 7. Open questions for the product owner (before implementation)

1. **Marketing consent.** Channel consent (Slice 5A) covers service
   messaging. Outbound marketing broadcasts (lead reactivation) need a
   separate consent basis and are proposed OUT of the first Growth slice.
2. **First publish destination.** Confirm Meta Pages/Instagram as the first
   live adapter (leverages the existing Operanto-managed Meta app), or name
   an aggregator to evaluate.
3. **Outrank account ownership.** Per-organisation Outrank accounts (each
   org pays/owns) vs Operanto-operated — affects only webhook secret
   handling, but changes the commercial story.
4. **Creative storage.** Where generated assets live (Vercel Blob vs S3)
   and their retention default.
5. **Navigation.** Growth becomes a nav entry only when the slice ships
   runtime ("no empty future capability pages" rule).
