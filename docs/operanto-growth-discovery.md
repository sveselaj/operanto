## 1. Domain model (proposed)

The prototype branch (`origin/mediasync-communication-layer`, untouched)
proved the shape of three entities on obsolete tenancy (`Workspace`,
6-role matrix). Everything below is REWRITTEN onto `OrgContext` +
`requirePermission` + `scope(ctx)`; nothing is ported verbatim.

| Model | Purpose | Prototype precedent | Notes |
| --- | --- | --- | --- |
| `BrandProfile` | Voice, tone, language, dos/don'ts, example phrases; the guardrail input to every content generation | `BrandVoice` (`brand-voices.ts`, working) | Extend toward a full profile: audience, offer positioning, banned claims. Contains no customer personal data. |
| `ContentDraft` | A generated, imported or hand-written piece of content, always local until explicitly published | `ContentDraft` + studio UI (working) | Reuses the AIAction/ApprovalRequest pattern from Slice 4: drafts are AI OUTPUT records, PII-reduced inputs, validated JSON, redaction joins retention. Provider-generated drafts (e.g. Outrank articles) import into this model carrying their provider article id. |
| `Campaign` | A named growth initiative with goal, period, target channel set and budget-of-effort | none (queue mock only) | Owns `CampaignItem`s; carries the attribution key (§5). |
| `CampaignItem` | One scheduled/published unit (article, post, template broadcast) with channel, scheduled time, publish state and provider record linkage | `queue_social_post` tool + mock social adapter | Delivery-state machine mirrors Message: `DRAFT → APPROVED → QUEUED → PUBLISHING → PUBLISHED / FAILED`, monotonic, DRAFT/APPROVED permanently local — the Growth analogue of RECORDED. Stores the provider's canonical id (e.g. Outrank article id) once known. |
| `GrowthInsight` | A conversation-derived observation ("5 enquiries this week asked about X") that can seed a draft | `insight-create-post` (prototype) | Generated by an AI task over aggregate, PII-scrubbed conversation stats; never quotes customer content verbatim without staff editing. |
| `AttributionTouch` | Records that a conversation/customer arrived via a campaign (§5) | none | Append-only, ids-only. |

Explicitly NOT in scope for a first Growth slice: audience segmentation,
lead-reactivation broadcasts (outbound marketing consent is excluded by
approved decision, §4), multi-variant testing, paid-ads management.

## 2. Non-negotiable platform invariants (inherited, not new)

1. **No autonomous external publishing.** Approving a draft records it;
   publishing is a separate, explicit human operation with a server-side
   recheck chain — the exact WhatsApp `sendWhatsAppMessage` pattern. No AI
   approval, cron, workflow or background process may invoke a provider
   publish call. The one sanctioned FAILED exit is an explicit human retry.
2. **Provider code behind adapters, deny-by-default registry.** Adapters per
   destination/provider; unknown channels have no adapter; an adapter that
   cannot resolve its destination refuses.
3. **Tenancy.** Provider credentials per organisation, AES-256-GCM under
   `OPERANTO_ENCRYPTION_KEY`, never in plaintext, never in audit metadata,
   decrypted only inside adapter calls. No cross-tenant fallback of any kind.
4. **Privacy.** Growth models join `eraseCustomer` and retention on day one
   (insights and drafts sourced from a conversation carry the conversation
   id; erasure redacts sourced content). Audit metadata is ids-only.
5. **Three-role model.** Reuse `templates:manage`-style granularity:
   proposed `growth:manage` (A/S) for profiles/campaigns, `growth:publish`
   (A/S) for the explicit publish operation, `growth:read` reuse via
   existing view permissions. No new roles.
6. **Feature flags.** Deployment-level flag plus per-connection publish
   gates, publishing default OFF — the WhatsApp stage-gate pattern. (No
   flag is created by this document.)

### 3.1 Outrank — bidirectional adapter design

Operanto both drives Outrank and listens to it. Two adapters, one provider.

**Outrank command adapter** (outbound API calls, org-scoped):

- authenticate with the organisation's encrypted, org-scoped API key
  (client-owned account; decrypted only inside adapter calls);
- manage products (the Outrank container an organisation publishes under);
- generate and manage keyword opportunities;
- pre-create and generate articles;
- fetch article content (for import into `ContentDraft`);
- replace articles (push an Operanto-reviewed revision back);
- retry publication;
- query Search Console performance for published articles;
- inspect usage and subscription state (surface quota/plan limits in the
  cockpit before staff trigger paid generation).

Command calls happen ONLY inside explicit, permission-checked staff
operations (`growth:manage` / `growth:publish`) — never from cron or AI.

**Outrank event adapter** (inbound webhook, store-then-process):

- receive published-article events;
- receive updated-article events;
- authenticate webhook calls (shared-secret signature verification before
  any tenant data processing — the WhatsApp route discipline);
- process through the canonical store-then-process event architecture
  (stored payload, atomic claim, bounded retries, dead-letter, retention);
- enforce tenant-scoped idempotency (unique per connection + provider
  event/article key — never a global key);
- link provider article ids to the canonical Operanto records
  (`CampaignItem` provider linkage / `ContentDraft` import linkage).

**Roles vs Outrank's own publishing:** Outrank publishes to the CMS
destinations it supports; Operanto orchestrates (what to write, when to
publish, retry) and records outcomes. Operanto is the system of record for
campaign state and attribution; Outrank is the system of record for article
delivery to the CMS. Operanto may actively orchestrate Outrank while also
consuming its lifecycle events.

### 3.2 Buffer — verification-gated classification

Classification: **potentially viable for multi-tenant integration, pending
hands-on OAuth client registration, scope verification, rate-limit testing,
partner/commercial confirmation and a proof-of-concept connection.**

- The documented App Client flow (OAuth 2.0, Authorization Code with PKCE,
  registered confidential and public clients, applications acting on behalf
  of Buffer users) is the candidate path for per-organisation connections.
- The personal API-key path is suitable only for account-owned workflows
  and is NOT sufficient for a polished multi-tenant SaaS connection.

**Buffer discovery task (pre-implementation; no runtime code in this PR):**

1. register a Buffer OAuth test client;
2. connect a test user;
3. retrieve organisations and channels;
4. create a scheduled test post;
5. revoke access;
6. verify refresh-token behaviour;
7. document scopes, rate limits and any account or plan restrictions.

The outcome of this task decides Buffer vs direct-platform adapters for the
social journey. No Buffer runtime code, OAuth implementation or credentials
exist in this repository.

## 4. Approved product decisions (recorded 2026-08-02)

1. **Outbound marketing-consent workflows are excluded from the first
   Growth runtime slice.** Channel consent (Slice 5A) covers service
   messaging only; no marketing broadcasts until a separate consent basis
   is designed and approved.
2. **The initial publication journey is article/SEO-first, not
   social-first.** Social publishing follows only after the Buffer
   discovery task (§3.2) or a direct-adapter decision.
3. **Outrank uses a client-owned account with an encrypted,
   organisation-scoped API key initially.** Each organisation owns its
   Outrank subscription and key; Operanto stores the key AES-256-GCM
   encrypted, org-scoped, never in plaintext or audit metadata.
4. **Bundled or reseller Outrank access requires separate contractual
   approval** before any architecture assumes it.
5. **Asset handling is metadata-first.** Provider-hosted assets are
   referenced by safe metadata; Operanto object storage holds only durable
   APPROVED assets, with explicit retention and erasure coverage.
6. **Growth navigation appears only when campaign creation, approval,
   publication and publication-result handling work end to end.** No
   placeholder pages at any earlier point.

## 5. Campaign → conversation attribution

Attribution is deliberately modest and honest: exact keys only, no
probabilistic matching (the identity-ladder philosophy applied to growth).

- **Key**: every `CampaignItem` carries a short code (`cmp_<id>`), woven
  into published URLs as UTM parameters and, for WhatsApp entry points,
  into a `wa.me` click-to-chat link's prefilled text.
- **Capture rungs (exact only)**:
  1. Pronatona web enquiries: the existing signed event envelope gains an
     optional `campaignRef` field (additive, ignored when absent) carried
     from UTM → lead → `AttributionTouch`.
  2. WhatsApp: a first inbound message whose text still contains the
     prefilled campaign code attributes the conversation, then the code is
     stripped from display.
  3. Manual: staff can attach a campaign to a conversation after verifying
     the linkage (select field, audited) — the fallback that always works.
- **Storage**: `AttributionTouch { organisationId, campaignItemId,
  conversationId, customerId?, capturedVia }` — append-only, ids-only,
  joins erasure via `customerId`.
- **Reporting**: campaign detail shows touches → conversations → linked
  customers → tasks/opportunities created, all as counts with drill-down
  through existing scoped queries. No cross-org aggregation, ever.

## 6. Provider adapter interfaces (sketch)

```ts
// Outrank command adapter — explicit staff operations only.
interface OutrankCommandAdapter {
  verifyConnection(connection: GrowthConnection): Promise<ConnectionStatus>;
  listProducts(): Promise<OutrankProduct[]>;
  generateKeywordOpportunities(productRef: string): Promise<KeywordOpportunity[]>;
  createArticle(spec: ArticleSpec): Promise<{ providerArticleId: string }>;
  fetchArticle(providerArticleId: string): Promise<ArticleContent>;
  replaceArticle(providerArticleId: string, content: ArticleContent): Promise<void>;
  retryPublication(providerArticleId: string): Promise<void>;
  fetchPerformance(providerArticleId: string): Promise<SearchPerformance>;
  fetchUsage(): Promise<UsageAndSubscription>;
}

// Outrank event adapter — data in, nothing executed.
interface OutrankEventAdapter {
  verifySignature(headers: Headers, rawBody: string,
    connection: GrowthConnection | null): boolean;
  dedupeKey(payload: unknown): string | null;   // tenant-scoped by connection
  receiveEvents(payload: unknown): NormalizedGrowthEvent[]; // published/updated
}

// Social publishing (post-verification) — mirrors ConversationChannelAdapter.
interface GrowthPublishAdapter {
  readonly destination: GrowthDestination;
  verifyConnection(connection: GrowthConnection): Promise<ConnectionStatus>;
  /** Explicit publish — called ONLY by publishCampaignItem's recheck chain. */
  publish(input: PublishInput): Promise<{ providerPostId: string }>;
  receiveEvents(payload: unknown): NormalizedGrowthEvent[];
}

// Creative — mirrors AIProvider (mock default, live opt-in).
interface CreativeProvider {
  readonly name: string;
  generateImage(spec: CreativeSpec): Promise<CreativeAsset>; // no PII in spec
}
```

`publishCampaignItem(ctx, itemId, idempotencyKey)` re-runs server-side:
deployment flag → `growth:publish` → org + record access → item is
APPROVED (never DRAFT) → connection active + publish-gate + credential →
brand-profile safety checks → idempotency claim before the provider call →
conditional `QUEUED→PUBLISHING` claim → provider → `PUBLISHED`/`FAILED`.

## 7. Validation journeys

### First candidate journey (article/SEO-first — the initial runtime target)

1. create or select a `BrandProfile`;
2. create a `Campaign`;
3. request keyword opportunities through an Outrank adapter;
4. select a keyword;
5. request an article draft;
6. import the draft into an Operanto `ContentDraft`;
7. review and approve it (local — the Growth RECORDED analogue);
8. perform a separate explicit publication operation;
9. receive Outrank's publication event through the event adapter;
10. create an `AttributionTouch` from exact UTM, campaign reference or
    manually verified linkage;
11. associate a resulting website or WhatsApp enquiry with the `Campaign`;
12. report the article → enquiry → Conversation → Task/Opportunity outcome.

### Vertical contexts

**Pronatona (real estate; primary context for the first journey):** a new
listing seeds the campaign above — keyword research, article generated and
reviewed, explicitly published, the buyer arrives through the article's
UTM-tagged enquiry form (`campaignRef` in the signed envelope) or writes on
WhatsApp; the identity ladder links them; campaign detail shows 1 article,
N enquiries, M viewings booked. Growth never contacts the buyer
autonomously at any point.

**Nagelista (retail; validates the same loop on commerce content):**
recurring gel-polish shipping questions surface as a `GrowthInsight` → an
FAQ/care article drafted against the Nagelista `BrandProfile` (mock AI in
staging) → reviewed, approved, explicitly published → shoppers arrive via
the article's wa.me link carrying the campaign code → attribution links
campaign → conversation → customer → order follow-up task. Social
amplification of the same content follows only after the Buffer discovery
task (§3.2) or a direct-adapter decision.
